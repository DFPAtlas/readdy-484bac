# Team Access management recovery

The published management screen searched app.users as an ordinary client, although that table correctly exposes only the caller's profile. It silently discarded search/exclusion failures, used a no-op Search button and joined member profiles that RLS hides. Permission toggles were optimistic and checked only errors; removal accepted zero-row success. Thrown requests and old callbacks could leave busy state or restore stale account data. These are source/regression findings; no production membership was created to reproduce them.

## Result

Search submits explicitly and requires the full verified Auth email of an existing active client account. Matching is exact and case-normalized, with no wildcard directory and no broader profile-table grants. Search excludes self, unavailable/closed/banned/unconfirmed accounts and anyone already in a team. Missing results and failed searches have separate states and Retry. Existing members' minimal names/verified Auth emails are projected only for their owning team; missing legacy profiles are explicitly unavailable.

manage_my_client_team derives auth.uid() and requires matching expected user/client context, the owner's own active client Team Access entitlement, active/non-suspended client and client user type, and confirmed/non-deleted/non-banned Auth identity. Inherited Team Access alone does not authorize managing another team. Member identity/email/eligibility and plan features are rechecked for changes. A unique member index enforces the existing single-owner rule; no legacy duplicates are deleted or reassigned. Read pages use 200-row cursors, owner scope and a consistent team revision; clients reject incomplete, foreign, duplicate, malformed or mixed-revision responses rather than invent an empty list.

Adds start with no delegated features. Changes use exact owner/member/config bindings, expected saved features and an owner-wide expected revision. Obsolete stored feature names can be removed but unavailable features cannot be newly enabled. Removal has explicit confirmation and verifies owned membership absence, including safe absent replay. Browser table/column INSERT/UPDATE/DELETE grants are revoked on both the public table and app security-invoker view. Three restrictive write policies preserve this boundary even after an accidental grant; existing owner/member SELECT and closure policies remain. The function has a fixed empty search path, no anonymous execution, and authenticated/service execution only. No resource-specific job/payment/message authorization is broadened.

## Lost responses and recovery

Each change has one stable operation UUID. Membership, team revision and a private operation receipt commit in the same database transaction. A receipt is bound to its owner, company and canonical request; it stores IDs/features and an email hash rather than raw email/profile names. Reusing a reference for a different change is rejected. Replays confirm the recorded outcome without applying the change again, even after subsequent edits/removal/re-addition. Revision checks reject a first-arriving old request after any newer managed change, including an edit that later returns to the same feature values. Returning-row, final-state, revision and receipt failures abort the whole transaction.

The UI does not change saved switches or remove rows before confirmation. One synchronous operation lock prevents overlapping writes. Uncertain results retain the same descriptor for explicit Retry; they do not claim that nothing happened. After a confirmed operation, a fresh owned read controls the display. If that read fails, the UI distinguishes a confirmed change from an unavailable current list and requires read Retry. A confirmed SQL rejection requires Reload before another change. Authentication checks have a 10-second deadline; RPCs have a 20-second deadline and abort the HTTP request on expiry. Aborting a request does not prove database rollback; the saved operation reference resolves uncertainty. Search/input/modal generations, owner/client generations, auth changes and unmount checks discard late callbacks. Same-user token refresh does not reset the page.

An already-received request may finish after navigation. Leaving loses the local pending descriptor; review current team state on return. Retried old operations cannot overwrite newer managed changes. Direct service/SQL writes are trusted administrative operations and do not automatically advance this RPC's revision; an entire multi-page read is not a cross-service snapshot. Operational receipts/revisions are service-only recovery metadata, with no automatic receipt purge/export-policy certification added here.
