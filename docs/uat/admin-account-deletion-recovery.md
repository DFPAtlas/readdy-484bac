# Admin account deletion deployment recovery

During the Documents repair, hosted admin-delete-user v33 was found to differ from the repository's retention safeguards. The v34 compatibility patch changed only client-files inventory. Its legacy account flow could delete booking/financial records, overlook service errors and report partial work as success. This repair replaces that runtime with the reviewed repository handler plus the checks below.

## Behavior

- Authenticate the bearer through Auth before parsing at most 8 KB. Require verified-token AAL2 and an active super_admin row bound to that caller. Retain self/last-admin/any-admin and cross-role protections.
- Treat user_id as the requested profile UUID. Require an exact returned profile ID, a valid non-null Auth user_id, one same-role profile and a matching Auth identity or explicit Auth user-not-found response. Never fall back to treating the profile ID as the Auth ID. Ambiguous empty Auth responses fail closed.
- Real deletion additionally requires confirmation exactly DELETE GUARD or DELETE CLIENT and expected_user_id matching the verified Auth identity returned by the impact check. The modal supplies both the typed phrase and reviewed identity; a profile rebind between checks cannot redirect that request. Older published clients cannot perform real erasure until the new frontend is published. An impact check still writes an audit; it is not a read-only production probe. The expected identity is a context check, not a new authorization credential or a signed impact snapshot.
- Booking, assignment, application/invitation/completion, review, support, complaint, client activity, financial and configured billing-provider evidence require review and block erasure. Client document metadata also blocks admin erasure pending the separate retention workflow. Existing account-closure/retention records also block this bypass. Provider identifiers on the profile, app.users or entitlement block even without local ledger rows. Responses/audits contain binding counts, not provider IDs. No provider cancellation, financial rewriting or ledger deletion is performed.
- Use actual app-schema tables; public.payment_audit_logs and public.payment_fee_breakdowns do not exist in the inspected project and are no longer queried. Write the actual public.admin_deletion_audit_log. Use the physical app.user_entitlements_data for eligible cleanup; the simple user_entitlements view was not established to be non-updatable.
- Confirm inserted/updated audit identity and status. Establish a non-success audit before any erasure. Storage cleanup uses recursive UUID-root inventory, the Storage API and absence checks. Unsupported legacy verification paths require review. Storage or progress-audit failures stop before profile/Auth deletion.
- Recheck binding, linked roles/admin access, retention and caller admin status at phase boundaries and before each storage batch. Check each returned row-deletion error and confirm absence. Verify Auth absence after deletion. Explicit profile deletion filters both profile ID and Auth user_id. Recheck personal rows and owned files after account cleanup. Missing/zero-row/mismatched audits, remaining records, transport errors and unconfirmed final auditing cannot return completed success. Return the audit ID for review.

## Validation

The regression harness runs the actual TypeScript handler and storage helper with synthetic Auth/database/storage services. Metadata-only production column and foreign-key captures dated 20 November 2026 validate every selected/filtered/written table and column in both account branches. Count-only reward/privacy fixture entries list their verified FK columns rather than an entire table schema. Auth-cascaded reward ledgers/redemptions/referral anchors and privacy requests are explicit review blockers. It catches nonexistent tables and does not simulate all database constraints, RLS, triggers, provider behavior or distributed concurrency.

Focused coverage includes authorization, bounded/invalid bodies, explicit confirmation, identity mismatch/missing binding, cross-role/duplicate profiles, provider-only and operational evidence, returned errors/null counts, nested/paged storage, unchanged bindings, silent database/Auth deletes, zero/wrong-row audits, thrown/zero-row progress/final auditing, explicit missing Auth recovery, and matching profile delete filters. No production impact-check, deletion, retention-worker invocation, file removal, provider call, email or message is used for validation.

## Acceptance and limits

Merge after green current-head CI, import latest main into Readdy and publish. The explicit server confirmation makes old frontend real deletion fail closed until publication. No database migration, new dependency, secret or provider configuration is required.

Controlled labelled synthetic fixtures must still establish positive eligible guard/client erasure, retained account blocking, missing Auth recovery, all legacy storage references, failures/recovery, session revocation and audit visibility in the published admin UI. Do not use an existing business account. Published positive acceptance is unconfirmed; broader account closure/retention, guard, booking, payments and communication journeys remain unsigned. Public launch remains on hold.

Database, Storage and Auth operations are separate and not atomic. Phase rechecks reduce drift but are not a transactional lock or a proof against concurrent booking/webhook/admin changes. A crash or late failure can leave partial erasure requiring manual review; after Auth removal, profile anchors may already be gone. A repeated impact check may not recover that case. The audit row is retained; no automatic rollback or full legacy/cascade footprint certification is claimed. Planned row totals can overlap where two ownership columns refer to the same record. External public profile images are outside owned storage cleanup. Do not roll back to legacy v34 to bypass a retention block.
