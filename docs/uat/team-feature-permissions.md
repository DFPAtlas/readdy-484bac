# Team feature permission repair

The all-client feature loader ignored enabled_features and inherited every feature in the owner's active entitlement. The single-feature reader applied the selection but attempted to read the owner's private entitlement from the member's browser. This is a source/regression finding, not evidence that a production member obtained unselected features: owner RLS normally prevents that read, and browser cache/session context also matters.

## Behavior and boundaries

The read-only app.get_my_team_features() function derives the member from auth.uid(), accepts no target-user parameter and returns only a sorted, distinct list of known client feature keys. Delegation requires exactly one membership, distinct owner/member, active client profiles with client user types, no closure record for either account, and the owner's own active client entitlement containing client.team_access. The returned keys are the intersection of enabled_features and that entitlement. Malformed data, absent/inactive entitlements, multiple owners, closed/inactive accounts and self-membership return no delegated rights. Inherited rights are not used to authorize another delegation chain.

The function has a fixed empty search path and schema-qualified relations. PUBLIC/anon execution is revoked; authenticated/service roles can execute. It makes no writes and exposes no owner ID, profile, billing fields or entitlement record. Production inspection confirmed app.team_member_configs is a security_invoker view over the RLS-protected public table, not an unprotected app table. Its owner/member policies, restrictive closure policy and the private entitlement RLS are preserved.

Both hasFeature and the all-feature loaders use that same effective team list. They never fetch an owner's private entitlement or team config to derive rights. Delegated rights are read afresh without the owner entitlement cache. Own plan features remain separate: turning a team switch off does not revoke something a member independently owns. Requested user/session context is checked before and after asynchronous work; late results after an account/new-sign-in change return no rights. A JWT session_id is only a browser lifetime hint, not authorization; normal refresh in the same session remains valid. Tokens lacking a usable session_id use the whole token as a conservative fallback. A supplied entitlement for another user cannot supply own features. Known client keys only are accepted from the RPC; lookup failures deny delegated rights while current own features remain available.

These browser helpers control presentation/navigation; they do not replace resource-specific server authorization. Revocation is observed on the next permission lookup; this patch does not push refreshes into already-rendered dashboard flags. This repair grants no access to another company's jobs, payments, profiles or messages and does not change business-data policies. It does not implement shared-company context, membership consent, invitations or recursive teams. The existing own-plan fallback/cache behavior remains separate.

## Validation and release

Tests execute the actual TypeScript helper and migration in a synthetic PostgreSQL environment. Coverage includes both readers agreeing, own/delegated separation, immediate revocation, RPC errors/malformed data, unknown/guard keys, foreign entitlements, anonymous/foreign sessions, account/token changes, active/closed/role/plan checks, multi-owner/self/nested ambiguity, private owner RLS, a real foreign team row, function privileges and no arbitrary target-user argument.

No production team member, invitation, permission switch, entitlement, profile, business record, message or email is changed. No production member credential is used. The additive read-only function deployment and full local/current-head CI evidence are recorded in the PR and consolidated smoke-test report. Until publication, the old browser loaders remain; deployment alone does not repair them.
