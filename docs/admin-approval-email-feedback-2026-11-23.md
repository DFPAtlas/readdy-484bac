# Approval decision and email acknowledgement

The deployed approval path (admin-verify-guard v76) saved a guard approval and invoked send-guard-approval-email inside a generic non-blocking wrapper. It did not inspect HTTP status or provider acknowledgement. The UI always reported approval success, while the confirmation promised a welcome email. Rejection already had separate email-result reporting; approval did not.

New approvals now return notification_status: accepted, already_sent or failed. Accepted requires a successful internal response with success=true and a nonempty string email_id; skipped=true is reported separately. Failed, non-2xx, malformed, missing-ID or unavailable responses remain unconfirmed, with a ten-second deadline for the email request. The already-saved approval is not rolled back or repeated when the email fails. Existing approval side effects, authorisation, reviewer recording, eligibility behaviour, promo/referral/token paths and notification semantics are preserved.

Already-approved/verified decisions return already_approved=true and notification_status=not_requested. They do not claim that a new email was requested or delivery checked, and keep the existing reviewer-recording behaviour. No automatic resend or new email-retry endpoint is introduced.

Normal and override approval share the same frontend contract. It checks session availability, the exact returned guard ID, action and approved/verified status before closing a review. It reports saved approval separately from email acceptance/deduplication/unconfirmed status, including unknown/older-server email responses. A synchronous shared lock blocks overlapping normal/override submissions. Unmounted, closed, changed or reopened review lifetimes reject late callbacks. An uncertain response keeps the review open and asks the admin to refresh the decision before retrying. The approval confirmation no longer guarantees an email or unrestricted platform access.

No approval, override, manual SIA verification, provider send, password reset, booking or financial action was executed against production while preparing this repair. Tests use mocked provider acknowledgements and do not establish inbox delivery.
