# Optional client and guard MFA

Implement on this branch only. Open a draft PR after implementation and CI; do not merge, publish or deploy. Existing admin MFA, authorization and financial controls must remain unchanged.

## Scope
- Audit existing login, OAuth callback, magic-link, session restoration, client/guard layouts, account settings, Supabase policies and Edge Functions. Reuse safe generic logic from lib/admin-mfa.ts and admin enrollment/challenge pages; never reuse admin privileges or admin-only routing.
- Add Security settings for both roles. MFA is optional; existing and new users without a verified factor retain normal login. Use Supabase native TOTP enrollment, challenge and verification, compatible with Microsoft and Google Authenticator. Display QR/manual setup key only during enrollment, never persist or log secrets. Show enabled only after successful verification; handle interrupted/duplicate enrollment safely.
- For enrolled users, require AAL2 after every new AAL1 login, including supported OAuth and magic-link flows. Preserve only validated same-origin return paths. Fail closed on unknown assurance state. Do not rely on a browser toggle or local storage for enforcement.
- Audit and enforce verified-factor/AAL2 requirements at the trusted API, database/RLS, storage and Edge Function boundaries for protected client/guard data and operations; verify behavior against direct API access and stale tokens, not just route redirects. Preserve tenant ownership checks and existing admin/service-role protections. Do not introduce privileged client-callable bypasses. Document any remaining enforcement gaps as release blockers.
- Require fresh factor verification for disabling or replacing MFA, and design a documented identity-verified recovery process without email-only or support-agent bypass. Audit factor changes without logging codes/secrets. Do not promise recovery codes unless a secure implementation is actually provided and tested. Consider session revocation after security changes and test provider behavior.
- Accessible mobile-friendly screens; clear errors, retry and cancellation behavior, no sensitive data leakage. Keep rollout disabled until backend enforcement and recovery are verified; ensure rollout controls cannot disable protection for already enrolled users.

## Acceptance tests
Both roles: opt-out normal login; enrollment with correct/incorrect code; abandoned setup; subsequent login challenge; direct URL/API/RLS/storage/Edge Function bypass attempts using AAL1; AAL2 permitted only for own resources; OAuth/magic-link/session refresh/deep links; factor removal/replacement and recovery abuse; stale sessions, concurrent actions, provider errors, cross-role/cross-account isolation, admin login and admin MFA regression. Use synthetic test accounts and non-production environment. Run repository lint, typecheck, build and relevant full regression/CI suites; report actual results and limitations. Provide migration and rollback plan preserving enrolled users' security. No live testing, merging or deployment; manual UAT separately.
