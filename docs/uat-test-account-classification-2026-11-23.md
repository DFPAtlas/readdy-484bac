# Protected UAT test-account classification

The November UAT seed writes protected Auth `app_metadata.uat_run_id` and `uat_persona` but omitted `guards.is_test_account`. Six existing guard-list rows were independently linked to those exact protected markers and the canonical persona manifest: four guard personas and two guard shells belonging to client personas. A test name, email alias, editable biography or user_metadata alone is not provenance. No client or app.users test flag exists in the current schema, so none is invented.

The seed now requires matching protected metadata and the expected email before reusing any existing Auth identity or resetting its password. It marks guard inserts/upserts as test-only, then confirms a user-scoped flag update for any existing guard shells, including client personas. Client profiles without a guard shell do not acquire one. A missing/failed acknowledgement stops the seed. The seed was tested with mocked Auth/database interfaces and was not run against production.

The separate data correction in scripts/ops/20261123-classify-owned-uat-guard-fixtures.sql targets exactly six reviewed guard IDs and expected user IDs/personas. It locks guard/Auth rows, validates protected run/persona metadata and canonical identity, refuses closed accounts, changes only the test flag and normal updated timestamp, and inserts one admin audit per correction. An unexpected profile change or audit failure rolls the entire statement back. An advisory lock and existing repair audits make replay idempotent. Approval status, SIA evidence, availability, billing IDs, entitlements, jobs and financial history are preserved. The flag intentionally applies existing test-account exclusion/placement rules to these positively identified synthetic records.

Direct authenticated guard updates currently have UPDATE permission on the flag, an owner RLS policy and no field-level protection. The migration adds a focused invoker-rights trigger for INSERT and UPDATE OF is_test_account. Non-admin browser callers cannot insert a test profile or change the flag in either direction. The existing active-admin predicate requires MFA; service operations remain supported. JWT role checks also protect calls made through a security-definer profile RPC. Function execution is revoked from public/browser roles; normal trigger execution is covered by database tests. Existing RLS, guard-protection triggers and approval rules are retained.

Regression evidence includes the old owner-update bypass, both update directions, insert defaults, a definer-RPC bypass attempt, normal profile edits, MFA-admin/service writes, migration replay, six scoped audits and replay, forged user metadata, changed identity, closed-account rollback, audit-failure rollback, owned seed reuse and refusal to overwrite an unowned Auth identity.

This is classification and access-control repair, not evidence of a valid SIA check or a new guard approval. The remaining approval-email UAT, operational/recovery items and final live payment/refund UAT remain separate.

Validation: all **1,137** unit/regression tests passed, including seven focused classification/UAT cases. Script syntax checks, repository/admin TypeScript and full lint passed; lint retains ten existing warnings and no errors. No frontend files changed, so a new local frontend build was unnecessary.

The protection migration was applied and verified in production. A rolled-back transaction using the controlled guard's authenticated database role received the intended classification-denied error. The guarded correction then marked exactly six reviewed profiles and created six audit records. Guard count remains 22; test-flag count increased from three to nine. Whole-row hashes excluding only the intended flag and normal update timestamp confirmed that all other guard fields were unchanged. Complete subscription, subscription-payment, entitlement and assignment hashes also matched before/after. No seed, Auth password reset, email, approval, provider call or financial action was executed against production.
